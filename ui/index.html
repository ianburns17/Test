Expected Architectural Conclusion: Returning 202 Accepted drastically reduces client waiting time for durable ingestion (< 30ms). It decouples HTTP ingestion from image decoding and scaling, but does not reduce the CPU work required by the background worker.
Week 1 Acceptance Gate & Defense Checklist: These 4 questions define the authoritative boundary of the ingestion system and must be defendable during evaluation.
1. Where does the selected file exist before submission? ▾
The selected file exists exclusively on the client machine's local storage and in the browser process sandbox memory as an in-memory DOM File / Blob object (accessed via <input type="file">).

When the browser renders the image preview, it creates an ephemeral client-side object URL (URL.createObjectURL(file)) pointing directly to the browser's local memory buffer. At this stage:
  • Zero bytes have crossed the network wire.
  • No HTTP request has been constructed or transmitted.
  • No file exists on the server's filesystem.
  • No database record or job has been created in PostgreSQL.
2. What work must finish before the server can safely return 202? ▾
Before the server can issue HTTP 202 Accepted, it must complete the full contract of acceptance responsibility:
  1. Size Enforcement: Ingest request body under an enforced memory ceiling via http.MaxBytesReader (10 MB).
  2. Authoritative Magic-Byte Validation: Read binary header bytes (first 512 bytes) and verify genuine image/jpeg or image/png using http.DetectContentType. Disguised payloads are rejected with 422.
  3. Server-Controlled Filename: Generate an unpredictable, collision-free UUIDv7 identifier with canonical extension. The client-provided filename is never used as a filesystem path.
  4. Durable Filesystem Persistence: Stream raw bytes to server disk (./storage/uploads/<uuid>.<ext>) and verify file closure succeeds.
  5. Durable Database Persistence: Insert the image metadata into images and the asynchronous job into jobs with initial status 'queued'.
  6. Location Header: Prepare the Location: /v1/jobs/<public_id> response header.
Critical Week 1 Rule: Image transformation (decoding, resizing, variant generation) must NOT run before returning 202; doing so synchronously breaks the decoupled acceptance boundary.
3. Why is the browser's file-type check not authoritative? ▾
The browser client is an untrusted, externally controlled execution environment. Any validation performed in the browser can be bypassed or forged:
  • Extension Forgery: An attacker can rename an executable or shell script from exploit.sh to exploit.jpg.
  • Header Spoofing: Non-browser tools (curl, Postman, custom scripts) can emit arbitrary Content-Type: image/jpeg multipart headers with arbitrary malicious payloads.
  • OS MIME Mismatches: Client-side MIME detection relies on OS registry extensions which may be manipulated.
Therefore, the server acts as the sole authoritative gatekeeper by sniffing binary magic numbers (e.g. 0xFF 0xD8 0xFF for JPEG, 0x89 0x50 0x4E 0x47 for PNG).
4. What does the disabled button solve, and what duplicate-request problem does it not solve? ▾
What it solves: The disabled button coupled with an in-memory isSubmitting boolean guard solves the single-session concurrent dispatch race condition. It prevents accidental double-clicks or rapid button mashing from initiating overlapping POST /v1/images requests from the same active browser page while the first is in flight.

What it does NOT solve:
  • Cross-Tab / Cross-Window Duplication: Multiple tabs maintain separate DOMs and independent memory states; both buttons are enabled.
  • Network Retries: Reverse proxies or client HTTP libraries retrying dropped packets dispatch duplicate requests.
  • Page Reloads: Refreshing the browser resets the DOM and enables the button again.
  • Automated Clients: Direct API scripts bypassing the browser entirely.
Solving multi-client duplicate submission requires backend idempotency keys or SHA-256 content-addressable deduplication.
