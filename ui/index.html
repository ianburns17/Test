Evaluation Defense & Architectural Answers
The 4 questions and the Week 2 architectural gate define the evaluation defense for durable jobs and background worker processing.
1. Why must the job be persisted instead of existing only in a goroutine or channel? ▾
1. Process Crash & Restart Resilience: If the Go application process restarts, crashes, is redeployed, or is terminated by an OS OOM event, in-memory goroutines, heap data, and channel buffers are instantaneously erased. Any accepted work existing only in-memory is permanently lost. Persisting jobs to PostgreSQL guarantees durability across crashes.

2. Independent Scalability & Contention Safety: In-memory Go channels are restricted to a single OS process. A relational database queue enables multiple worker processes across a cluster to safely claim work using atomic concurrency primitives (FOR UPDATE SKIP LOCKED) without double-processing.

3. Client Observation & Disconnect Survival: Short polling requires that any client session, page reload, or alternative device can query GET /v1/jobs/{job_id} at any time. A database-backed job record ensures consistent, authoritative state visibility independent of transient client network disconnects.
2. What does 202 Accepted guarantee, and what does it not guarantee? ▾
What 202 Accepted GUARANTEES:
  • The server has received, parsed, and verified the upload against size and magic-byte constraints.
  • The original file bytes are durably written to server filesystem storage (./storage/uploads/).
  • A persistent job record has been created in PostgreSQL with status 'queued'.
  • A canonical job resource URL is provided in the Location header and response body for polling.
What 202 Accepted DOES NOT GUARANTEE:
  • It does not guarantee that processing has started.
  • It does not guarantee that image transformation will succeed (the worker may fail due to corrupted payload).
  • It does not guarantee that any variant files exist yet.
  • It does not reduce total CPU computation or eliminate queue waiting time.
3. Who owns authoritative job state? ▾
The PostgreSQL Database (specifically the jobs table) owns authoritative job state.

Neither the browser client, nor the HTTP request handler, nor the in-flight background worker owns authoritative state:
  • The Browser Client: Only holds an ephemeral, potentially stale cached observation retrieved during the last short poll.
  • The HTTP Handler: Exits immediately after inserting the 'queued' row and returning 202; its execution lifetime terminates before processing begins.
  • The Background Worker: Is merely an execution agent that claims work and proposes state mutations; it must commit status updates ('processing', 'completed', 'failed') to PostgreSQL.
The database enforces constraints (the job_status enum) and atomic locks (FOR UPDATE SKIP LOCKED), making PostgreSQL the sole source of truth.
4. Why does one worker make queueing visible when several jobs are submitted? ▾
With exactly one background worker running in the application (concurrency $C = 1$), the processing pipeline is strictly serial.

When multiple uploads are submitted close together (such as a burst of 5 images):
  1. The HTTP server accepts all 5 jobs in $< 25\text{ms}$ each and commits them to PostgreSQL with status 'queued'.
  2. The single worker claims Job #1, transitioning it to 'processing'.
  3. Jobs #2, #3, #4, and #5 must remain in PostgreSQL in the 'queued' state until Job #1 finishes.
  4. Consequently, the Queue Wait Duration ($T_{\text{queue}} = \text{started\_at} - \text{queued\_at}$) visibly increases for each subsequent job in the burst.
This proves that asynchronous acknowledgment reduces client waiting for ingestion, but cannot bypass throughput bottlenecks under limited worker capacity.
Week 2 Architecture Gate Compliance ▾
CRITICAL GATE: "An application that returns 202 but performs transformations in the request handler has not implemented the required architecture."

In our implementation:
  • uploadImageHandler in cmd/api/images_handlers.go performs zero decoding, resizing, or variant generation. It returns 202 in < 25ms.
  • A distinct background worker goroutine running in cmd/api/worker.go polls PostgreSQL and claims jobs via FOR UPDATE SKIP LOCKED.
  • The database visibly transitions from queued to processing to completed (or failed).
  • All 3 variants (thumbnail 150x150 square, preview ≤ 800x600, display ≤ 1200x900) are generated strictly by the worker.
