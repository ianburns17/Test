ImageLab Version 2 Requirements
Versioned long polling and progress observation
Companion to Assessment 2 | Extension of the completed Version 1 application
1 Purpose and existing contracts
Add version-based long polling alongside the existing short polling. The browser observes work; the worker performs it; PostgreSQL owns the authoritative job. Existing image-processing knowledge is assumed.
Keep POST /v1/images, the 202 response and Location header, local storage, one worker, and the original variant endpoints. Keep queued, processing, completed, and failed as the only job states. Preserve thumbnail 150 × 150 crop, preview within 800 × 600, and display within 1200 × 900 with preserved aspect ratios for preview and display.
Version 1 requirements remain in force unless explicitly changed here. The new observation modes and progress fields replace the short-polling-only restriction. The assessment brief supplies experiment and submission requirements.
2 Terms used in this specification
Term
Meaning
Representation
The job information returned in a response, including status, progress, version, and available result metadata.
Version
A positive integer that increases when the job’s observable information changes. It is not a percentage.
Snapshot
The current representation. It does not contain a history of every earlier change.
Notification
An in-process signal telling waiting observers to recheck persisted state.
Holding deadline
The maximum time the server waits for a newer version before returning a normal no-change response.
Terminal state
Completed or failed. No further worker progress updates are allowed.


3 Persistent version requirements
VER-01 Create jobs at version 1. Backfill existing jobs with a valid initial version. Persist the version in PostgreSQL and return it in every successful job representation, including prompt short-poll responses.
VER-02 Increment the version in the same database transaction as each observable status or progress change. Keep representation fields and version consistent. Reads, holding-deadline expirations, and duplicate notifications must not increment it.
VER-03 Notify observers only after commit. All observers of the same job must be able to discover a change; a single shared channel receive that wakes only one observer is insufficient. Notifications may be coalesced because the database retains the latest snapshot.

4 HTTP observation contract
API-01 GET /v1/jobs/{id} without query parameters remains a prompt snapshot response. It must never wait for a change. Both modes return the same representation fields.
API-02 GET /v1/jobs/{id}?after=7&wait=20 requests a snapshot newer than version 7, waiting up to 20 seconds. after is a nonnegative integer. wait is an integer from 1 to 20 seconds and defaults to 20 when after is supplied. Reject wait without after, malformed values, and out-of-range values with 400.

404 promptly.

API-03 Use Cache-Control: no-store for observation responses. A 200 response is a complete JSON snapshot with the existing job fields plus version, stage, and variants_completed. Completed responses still include all three variants.
Example active snapshot: id=42, image_id=108, status="processing", version=4, stage="preview_ready", variants_completed=2. Existing queued_at, started_at, and terminal timestamps remain part of the representation.
5 Waiting and notification correctness
WAIT-01 Reuse the Counter + Version waiting approach. Register or capture the change signal and check persisted state in a synchronized order that cannot miss a change between checking and waiting. After a wake-up, recheck the version; a signal alone is not a representation.
WAIT-02 Wait without a busy loop. Release subscriptions, timers, and handler resources after every exit path. Request-context cancellation ends observation, not the worker’s job.
WAIT-03 Ensure server write deadlines and any proxy deadline permit the 20-second hold plus response time. Set the browser request timeout to 30 seconds for the lab. A normal server 204 and an actual client timeout have different meanings.

6 Browser and progress requirements
UI-01 Provide Short polling and Long polling controls. Show the selected mode, job ID, last observed version, status, and progress. Use the same rendering function for both modes.
UI-02 Start observation after acceptance. Fetch an initial prompt snapshot, save its version, then use the chosen mode. Short polling remains approximately one second. Long polling sends after equal to the last successfully received version.
UI-03 After a valid active 200, render and immediately send the next long poll. After 204, keep the last version and immediately send another long poll without parsing JSON. After completed or failed, render and stop.
UI-04 Maintain at most one outstanding observation request per page. On a mode change or new observed job, cancel the old loop and ignore its late responses using an observation generation/token or equivalent guard. Switching modes must not submit another image.
UI-05 On network failure, actual client timeout, non-success response other than the normal 204, or invalid JSON/representation, stop and preserve the last known state. Show Unable to check status and Try again. Try again observes the same job using the selected mode. Never infer worker failure from a retrieval error.
7 Real image progress
PROG-01 Add variants_completed from 0 to 3 and a stage describing current work. After each actual variant file and its metadata are stored, persist the new count and stage with a version increment, then notify. The status remains processing until all three outputs are available.
PROG-02 Suggested stages are starting, thumbnail_ready, preview_ready, and display_ready. The last variant milestone and completed status may share one transaction and version increment. Do not invent a fifth job state for a stage.
PROG-03 Display progress during processing without exposing partial results as a completed job. A failure keeps the last known progress but uses status failed and a safe error. No further progress updates follow terminal status.
8 Experimental controls
EXP-01 Implement disabled-by-default controls for the 30-second quiet delay and the 10-second simulated update phase. Record the configuration for every run and use it unchanged for both observation modes.
EXP-02 Use a separate simulation_step or simulated_progress field for the timed phase. Label it Simulated progress in the UI; keep variants_completed truthful. Each simulated change increments the persisted version. Log actual commit times rather than assuming timers fire exactly on schedule.
EXP-03 Complete the simulated phase before real transformations begin. Mark completed only after real image processing succeeds. Disable simulation when demonstrating ordinary ImageLab use.

9 Acceptance checks
Check
Required evidence
Baseline preserved
One-second short polling still works with the existing upload, worker, and results.
Old version
A request with an older version returns promptly with a consistent newer snapshot.
Wait and notify
An unchanged active job holds a request; a committed update releases it.
Change between requests
Produce an update before the next request arrives; the next request returns the newer snapshot immediately.
No change
An unchanged request returns 204 at the holding deadline; the next begins without an error or JSON parsing failure.
Two observers
Two tabs observing the same job both discover a change. This is a correctness check outside the single-observer experiment.
Terminal stop
Both completed and failed stop observation. Reopening an existing terminal job returns promptly.
Cancellation and switching
Old observation stops and late responses are ignored; worker progress continues.
Retrieval failure
A disconnected observation preserves state; Try again observes the same job without POST.
Progress and simulation
Real counts match stored variants; simulation is labelled, repeatable, and disabled for normal operation.
Measured comparison
Required runs, timestamp method, raw logs, charts, and evidence-backed report are included.


10 Interpretation and definition of done
A version gap shows that intermediate snapshots were not received. It does not, by itself, prove that the final result or stored data was lost. This API returns current state and does not promise replay of every event.
Fewer browser requests do not establish lower total resource use. Describe held handlers, notification bookkeeping, and any database polling. A new long-poll request does not necessarily create a new TCP connection; HTTP can reuse connections.
Version 2 is complete when both modes work against the same durable jobs, lifecycle checks pass, progress is truthful, and the comparison is reproducible. Your explanation must connect observed request behavior to your recommendation and identify what a continuing response could change.
Further reading after completing predictions: RFC 6202, sections 2 and 3, https://www.rfc-editor.org/rfc/rfc6202.html. This is supporting material; the assessment does not require implementing HTTP streaming.
