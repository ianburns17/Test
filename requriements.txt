ImageLab Version 3 Requirements
Server-Sent Events for versioned job observation
Companion to Assessment 3  |  Extension of the completed Version 2 application
This specification defines the required behavior for adding Server-Sent Events (SSE) to ImageLab. The existing upload and image-processing system remains in place. Version 3 changes how the browser observes a job: in addition to short and long polling, it can keep one SSE response open and receive complete job snapshots as the job changes.
CENTRAL CONTRACT
The worker performs the image job and PostgreSQL stores authoritative job state. The SSE handler observes committed versions and sends snapshots over one open response. Losing that response stops observation; it does not stop the job.

1. Existing contracts and scope
Version 1 and Version 2 requirements remain in force unless this specification changes them. Preserve POST /v1/images, its 202 Accepted response and Location header, durable job creation, one in-process worker, local image storage, the queued / processing / completed / failed states, and all-or-complete availability of the three required variants.
Keep short polling and version-based long polling working. Add SSE as a third observation mode. The required controlled comparison is SSE versus long polling. Do not rebuild image transformations or change their outputs.
In scope
Out of scope
SSE endpoint, complete job snapshots, named events, flushing, lifecycle, reconnection, and cleanup.
WebSockets, brokers, Redis, PostgreSQL LISTEN/NOTIFY, multiple workers, and multi-server fan-out.
Committed job versions and in-process notification to all active observers.
Durable event history, Last-Event-ID replay, exactly-once event delivery, and backend idempotency.
Controlled comparison, reproducible logs, tables, graphs, and an in-class presentation.
Claims about million-client capacity or production-scale capacity from this classroom experiment.


2. Job snapshot and version requirements
ID
Requirement
JOB-01
PostgreSQL remains the authoritative source for every job representation sent through SSE.
JOB-02
Every client-visible job representation includes the existing fields and the persisted version, stage, and variants_completed. Completed snapshots include all three variants; failed snapshots include a safe error.
JOB-03
Increment version in the same database transaction as each client-visible state or progress change. This includes queued to processing even when variants_completed remains 0.
JOB-04
Persist each real variant and its metadata before publishing the corresponding progress version. Do not expose partial variants as completed.
JOB-05
Keep simulated progress in a separate field, label it as simulated, and disable it for ordinary use. A timer never transitions a job to completed.
JOB-06
Completed and failed are terminal. No progress update follows a terminal state.


3. SSE HTTP and event-frame contract
ID
Requirement
SSE-01
Expose GET /v1/jobs/{id}/events for the browser EventSource API. Keep the existing prompt snapshot and long-poll endpoints available.
SSE-02
Return 404 for an unknown job before beginning a stream.
SSE-03
Set Content-Type: text/event-stream; charset=utf-8 and Cache-Control: no-cache before writing the response body. Disable intermediary buffering where the deployment proxy supports it.
SSE-04
On connection, send the current complete job snapshot immediately as a named job-update event.
SSE-05
After each newly observed committed version, send a complete current snapshot as a job-update event. The data is a snapshot, not a delta requiring earlier events.
SSE-06
End each event with a blank line and flush after writing it. Flush makes the frame available; it does not end or keep open the response.
SSE-07
Keep the handler and response open while the job is active and the request context remains active. End the server stream after sending a terminal snapshot or when the request ends.
SSE-08
Optionally send periodic SSE comment heartbeats on idle streams. A heartbeat is not a job-update event and does not change the job version.
SSE-09
Do not emit SSE id fields or claim Last-Event-ID replay in this version. The application version in the JSON snapshot is a state version, not an event-history cursor.


Required frame shape: event: job-update, followed by data: and a JSON snapshot, followed by a blank line. The JSON version identifies the snapshot revision. It does not promise that every intermediate revision will be delivered.
4. Synchronization and notification requirements
ID
Requirement
SYNC-01
Publish an in-process notification only after the database transaction containing the new job version commits.
SYNC-02
Notify every active observer of the job. A single shared channel receive that wakes only one observer is insufficient.
SYNC-03
Use a subscribe/read/wait order that cannot miss a job change between reading the current snapshot and waiting for the next notification.
SYNC-04
Treat a notification only as a signal to re-read PostgreSQL. Never construct an authoritative SSE payload from the signal alone.
SYNC-05
After waking, read the latest snapshot and send it only if its version is newer than the last version sent on this stream. Notifications may be coalesced, so version gaps are permitted.
SYNC-06
Release subscriber registrations and timers on every handler exit. Do not hold a mutex while waiting, querying the database, or writing to the network.
SYNC-07
Request cancellation ends the observer handler only. It must not cancel or fail the background image job.


5. Browser behavior and lifecycle
ID
Requirement
UI-01
After accepting a job, provide a selectable SSE observation mode for that same job ID. Opening the stream must not submit another image.
UI-02
Create one EventSource for the selected job and listen for job-update events. Parse event.data as JSON and pass the snapshot to the same renderer used by short and long polling.
UI-03
Show an initial snapshot promptly, then update status, stage, version, and progress from later snapshots. Do not expose completed results before the terminal completed snapshot.
UI-04
On EventSource error, show a reconnecting/connection message. Do not mark the job failed. Keep the same EventSource object so browser reconnection can occur.
UI-05
When a reconnect opens a new GET, the server sends the latest snapshot. Do not create another job or upload the image again.
UI-06
On completed or failed, render the terminal snapshot and call EventSource.close() so the browser does not reconnect for a finished job.
UI-07
Provide a stop-observing control or equivalent cancellation path. Closing observation must leave the worker and job unchanged.
UI-08
If observation is explicitly resumed, open one new EventSource for the same job. The initial snapshot must recover the current display state.


6. Measurement and visual evidence requirements
Complete a paired comparison of SSE and long polling for three conditions with three repetitions per method: 18 runs total. Use the same input and transformation settings, one observer during measured runs, an empty worker queue at each start, and alternating method order. Keep the tab in the foreground and record the actual workload configuration.
ID
Requirement
MEAS-01
Run a 30-second quiet active interval with no client-visible progress, then complete real processing.
MEAS-02
Run ordinary image processing and publish real progress only after each variant and its metadata are stored.
MEAS-03
Run a labelled 10-second simulated progress phase with updates every 200 ms, then complete real processing. Keep simulated progress separate from variants_completed.
MEAS-04
Keep client and server logs sufficient to join each observer run by job ID and version. Log the actual server commit time and browser receipt time.
MEAS-05
Record observation GETs, SSE stream GETs, SSE job-update events, heartbeats separately, received versions, version gaps, processing duration, terminal detection delay, observer database reads if applicable, stream duration, and peak active SSE handler count.
MEAS-06
Submit a run-by-run table and a summary table containing every repetition and the median plus minimum-maximum range for each condition and method.
MEAS-07
Submit at least two graphs generated from the recorded measurements: observation GET count by condition and method, and completion-detection delay in milliseconds by condition and method.
MEAS-08
Graphs must show the individual repetitions and a summary, have meaningful titles, labelled axes with units, and a readable legend. Explain each graph alongside its table.
MEAS-09
Tables and graphs are both mandatory. A graph does not replace raw logs or tables, and a table does not replace a graph.
MEAS-10
Count HTTP requests and SSE streams, not TCP connection establishments. Do not infer total resource cost or large-scale capacity from request count alone.


Recommended run columns: run_id, condition, mode, repetition, job_id, image, baseline_version, terminal_version, observation_gets, sse_stream_gets, job_events_received, heartbeats, versions_received, version_gaps, processing_ms, detection_ms, observation_db_reads, stream_seconds, peak_active_streams, notes.
7. Acceptance checks
Check
Pass evidence
Initial stream snapshot
Opening SSE for an active job returns its current version and remains pending.
Committed update
A worker commit produces a newer snapshot in every observing tab.
No missed change
An update occurring around subscription or reconnection is available in the next snapshot.
No false progress
queued to processing advances version even when variants_completed remains zero; simulated progress is not counted as a stored variant.
Version coalescing
A delayed observer may skip intermediate versions but receives a current snapshot, including the terminal version.
Disconnect
The SSE handler unsubscribes; the worker continues; EventSource reconnects and receives the latest snapshot.
Terminal state
Completed and failed snapshots render once, the client closes EventSource, and no further reconnect is made.
Multiple observers
Two tabs both receive updates for one job.
Comparison evidence
All 18 runs are accounted for; tables and both required graphs agree with the raw records.


8. Student explanation and presentation
Each student or project team will present the implementation and findings in class. The presentation must show the request/event lifecycle, a live or recorded DevTools trace, both required graphs, the measurement tables, and an evidence-based interpretation. Students must explain why fewer HTTP requests do not by themselves prove lower total resource use.
What does the GET open, and what does Flush do?
How do workers, PostgreSQL versions, notifications, SSE handlers, and browser listeners fit together?
What does a disconnect change, and what remains active?
Why does this specification recover a snapshot instead of replaying all missed events?
What do the tables and graphs show, and what limitations remain?
9. Definition of done
Version 3 is complete when ImageLab preserves its Version 2 contracts, sends correct versioned snapshots through SSE to all active observers, handles disconnects and terminal states without confusing observation with job execution, passes the acceptance checks, and produces reproducible comparison evidence in both tables and graphs for the in-class presentation.
